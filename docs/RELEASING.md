# Releasing the Windows build

Releases are built by GitHub Actions ([`.github/workflows/release.yml`](../.github/workflows/release.yml)),
never on a developer machine, so a release can only contain what is in the public repository.

## What a release contains

| File | Purpose |
|---|---|
| `neural-thinker-<version>-windows-x64-setup.exe` | Installer (Inno Setup). Per-user install, no administrator rights; shows the license, which must be accepted, and the notice; adds a Start menu entry and an uninstaller. |
| `neural-thinker-<version>-windows-x64.zip` | Portable build: `neural-thinker.exe`, `LICENSE.txt`, `NOTICE.txt`. |
| `SHA256SUMS.txt` | SHA-256 checksums of both files. |

The executable is the Community edition built with `cargo build --release --locked`. It
carries the app icon and Windows version information (product name, version, copyright and
license note, see `build.rs`). The license and the `Required Notice` are also shown in
**Help → About** and linked from the welcome screen.

## Cutting a release

1. Merge the work to release into the branch you release from (normally `main`).
2. Set `version` in `Cargo.toml` (for example `0.2.0`, or `0.2.0-beta.1` for a pre-release),
   run `cargo check` so `Cargo.lock` follows, and commit.
3. Tag that commit and push the tag:

   ```sh
   git tag v0.2.0
   git push origin v0.2.0
   ```

4. The **Release (Windows)** workflow runs the private-code guard, builds and packages on
   `windows-latest`, checks that the tag equals `v` + the `Cargo.toml` version, and creates a
   **draft** release with the three files. Versions with a `-` suffix are marked as
   pre-releases.
5. Open the draft under *Releases*, review the notes and files, and press **Publish release**.

If the tag does not match the version, the workflow fails and nothing is released: delete the
tag (`git push --delete origin v0.2.0` and `git tag -d v0.2.0`), fix the version, and tag again.

## Dry runs

Every push to `dev/supervision` that touches the packaging files (the workflow,
`scripts/package-windows.ps1`, `packaging/`, `assets/`, `build.rs`, `Cargo.toml`,
`Cargo.lock`) runs the same build without creating a release. The files are kept as the
`neural-thinker-windows` artifact of that workflow run, so they can be downloaded and tested.
Once the workflow is on the default branch it can also be started by hand from the
*Actions* tab (*Run workflow*).

## Building the package locally

On Windows with PowerShell 7 (`pwsh`) and, for the installer,
[Inno Setup 6](https://jrsoftware.org/isinfo.php):

```powershell
pwsh scripts/package-windows.ps1              # zip and installer
pwsh scripts/package-windows.ps1 -NoInstaller # zip only
```

The files land in `target/dist/out/`. Local packages are for testing only; published releases
always come from the workflow.

## How private code is kept out

- The `private-guard` job runs `scripts/check-private.sh --history` and must pass before
  anything is built.
- The workflow builds from a fresh checkout, where the git-ignored `src/private/` cannot exist;
  the packaging script fails if it does.
- The packaging script fails if any crate named like the private one is in the dependency
  graph, if the package holds anything other than the three allowed files, or if any of them
  contains the private marker or the private crate's name.
- Releases are drafts until published by hand.

## Changing the icon

`assets/icon.ico` (embedded in the executable and the installer) and `assets/icon.png` (window
icon) are generated by `python3 scripts/make-icon.py` (needs Pillow).
